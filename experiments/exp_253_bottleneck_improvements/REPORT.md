```text

  ↓
```

- 실제 DW Showcase는 시작할 때마다 720MB 가격 CSV와 101MB 구성종목 CSV를 다시 검색했음

## 기존 병목

### 병목 1 — 필요한 결과보다 훨씬 많이 계산함

- FF3 팩터 조합에 필요한 것은 날짜별 계좌가치와 수익률뿐임
- 기존 전체 보고서는 아래 작업도 함께 수행함
  - 모든 종목별 보유내역 읽기
  - 종목별 손익 계산
  - 매매와 회전율 계산
  - 목표 비중과 실제 보유 차이 계산
  - 감시 결과 정리
- 기존 FF3 측정에서는 이 단계가 약 110초였음
- 당시 실제 실행 기록은 현재 작업공간에 없어 같은 FF3 전체를 다시 실행하지 못함

### 병목 2 — 같은 큰 원본을 매번 다시 읽음

- 실제 DW 전략 두 개에서 자료 추출이 전체 시간의 88.6%였음
- 전략 계산은 0.2초 안팎인데 자료 준비가 약 7초였음
- 같은 기간과 같은 종목인데도 매 실행마다 원본 CSV를 처음부터 검색했음

### 병목 3 — 여러 알파의 반복 준비

- 알파가 늘면 자료 검사, 실행, 중간 결과 등록도 거의 함께 늘어남
- 다만 각 실행은 어떤 자료와 코드로 만든 결과인지 따로 증명해야 함
- 하나의 살아 있는 데이터베이스 연결을 실행 사이에서 몰래 공유하면 자료 변경을 놓칠 수 있음

## 가설과 개선안

### 가설 1 — 성과만 골라 읽으면 빨라짐

- 가설
  - 종목별 행을 읽고 버리는 일이 보고서 병목의 대부분임
- 개선
  - 새 `strategy_performance` 경로를 추가함
  - 저장 파일 단계에서 계좌 합계 행만 고름
  - 시간·현금·계좌가치 등 필요한 열만 읽음
  - 수익률과 위험지표 계산식은 기존 것을 그대로 사용함
- 사용 판단
  - 수익률·샤프지수·낙폭만 필요하면 새 경로를 사용함
  - 종목별 손익과 체결 분석도 필요하면 기존 전체 보고서를 사용함

### 가설 2 — 준비된 DW 자료를 재사용하면 빨라짐

- 가설
  - 원본과 요청 조건이 같으면 같은 Parquet가 만들어지므로 다시 검색할 필요가 없음
- 개선
  - 기간·종목 수·원본 파일 위치·크기·수정 시각으로 식별값을 만듦
  - 같은 식별값의 준비 파일이 있으면 그대로 복사함
  - 원본이나 요청 조건이 달라지면 자동으로 다시 추출함
  - 투자 실행 결과는 캐시하지 않음

### 가설 3 — 여러 알파의 준비를 한 번으로 합치면 빨라짐

- 시험 판단
  - 개선 후 다시 잰 작은 다중 알파 예제는 기존과 사실상 같은 수준임
  - 인핸스드 인덱스 1.819초 → 1.747초임
  - 두 알파 결합 2.016초 → 2.040초임
  - 신호 측정 1.368초 → 1.380초임
  - 세 알파 결합 2.345초 → 2.373초임
- 결론
  - 차이는 실행 잡음 수준이며 10% 기준을 통과하지 못함
  - 독립 실행의 안전성을 포기할 근거가 없어 적용하지 않음

## 남은 개선 영역

- 실제 전략 계산의 가장 큰 공통 비용은 과거 자료 조회와 사용자 신호 계산임
- 다음 우선순위는 DataModel 결과의 안전한 증분 구체화임
  - 어제까지 확정된 결과를 유지함
  - 오늘 새 자료만 붙여 필요한 구간만 다시 계산함
  - 원천 자료·코드·설정이 같다는 증명이 필요함
- 보유종목이 많은 전략은 계좌 평가와 종목별 기록 저장도 추가 후보임
  - 같은 시점의 가격을 한 번만 찾는 방식
  - 종목별 Python 객체 생성을 줄이는 방식
  - 기록을 작은 묶음으로 계속 저장하는 방식
- 이 후보들은 실제 10년·전체 종목 전략 기록을 확보한 뒤 별도 기준으로 시험해야 함
