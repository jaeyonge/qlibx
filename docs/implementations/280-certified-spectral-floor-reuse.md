## 왜 이 변경이 있는가

실제 309종목, 2,096거래일, 64개 위험 상황을 계산한 실험에서 기존 14분 42초 중 14분
29초가 DataModel 실행이었음. 그 안에서 최종 점수 하나를 얻기 위해 위험 행렬 전체를 매번
분해하는 일이 주병목이었음.

전체 고유값과 고유벡터를 만드는 대신 고유값만 먼저 검사하고 행렬을 직접 풀면 첫 실행이
10분 40초로 줄었음. 동일한 입력의 안전 검사를 재사용한 반복 실행은 1분 52초~2분 5초였음.
팩터 parquet 419,576행과 경제적 전략 결과는 같았음.

실험 코드는 고정된 파일명, 기간, 종목 수를 전제로 했으므로 다른 사용자가 쓸 수 없었음.

## 무엇이 어떻게 바뀌었는가

- `signals/risk.py`에 `SpectralFloorSolver`를 추가함.
- 처음 보는 행렬은 고유값을 검사함.
- 보정이 필요 없고 수치 오차 여유도 충분한 행렬만 SHA-256 지문으로 증명함.
- 같은 설정, NumPy 버전, 행렬 바이트가 다시 오면 검사만 생략하고 직접 풀이함.
- 보정이 필요하거나 경계에 너무 가까우면 기존 전체 분해 공식을 그대로 사용함.
- 입력 행렬이 한 바이트라도 달라지면 새 행렬로 검사함.
- 깨진 파일이나 다른 설정의 파일은 건드리지 않고 무시함. 결과는 같고 검사 시간만 다시 듦.
- 캐시는 모델 상태나 결과 권위가 아닌 파생 증거임. 사용자가 경로를 명시해야만 생성됨.
- 검사, 신규 증명, 재사용, 전체 분해 횟수를 JSON으로 기록할 수 있음.
- 공개 이름은 하나뿐인 저자 표면 `vqapr.public`에서도 내보냄.

## 대안과 판단

- DataModel의 `memory`에 지문 13만 개를 넣지 않음. 매 콜백 저장 비용이 커지고 작은 JSON 상태라는
  역할을 벗어남.
- 전략 전용 private payload를 DataModel에 몰래 적용하지 않음. 현행 엔진 계약에 없는 통로임.
- 파일 전체 해시 하나로 모든 행렬을 신뢰하지 않음. 코드나 일부 기간 변화 때 새 행렬만 다시
  확인할 수 없고 실험 조건에 묶임.
- 행렬 생성의 증분화는 채택하지 않음. 실험에서 해당 단계만 1.46배였고 전체 절감은 약 2초였으며
  마지막 숫자와 재시작 상태가 달라졌음.
- C 재작성은 채택하지 않음. 주병목인 행렬 분해는 이미 NumPy 아래의 최적화된 네이티브 코드에서
  수행됨.

## 남은 한계

- 첫 실행은 모든 새 행렬을 검사해야 하므로 반복 실행보다 느림.
- 직접 풀이와 전체 분해는 일반적으로 마지막 부동소수점 비트까지 같다고 약속할 수 없음. 실험의
  팩터 파일은 같았지만, 다른 모델은 경제적 동일성과 필요한 허용오차를 별도로 확인해야 함.
- 같은 캐시 파일을 여러 프로세스가 동시에 쓰는 대규모 시험은 완료 검증에 포함해야 함.
- DataModel의 공식 private payload가 생기기 전까지 캐시는 framework-managed model state가 아님.
